# Experimental bounded snapshot download

The opt-in `GET /v1/snapshot?share=...&path=...` handler uses the same bearer authentication, per-share scope, and confined source root as the existing download handler. It does not change the legacy `/v1/download` behavior.

For regular files up to 8 MiB, the agent reads the entire representation into a bounded in-memory buffer, hashes the captured bytes with SHA-256, and emits a quoted strong ETag. A client first requests the complete representation to learn the ETag, then sends both `Range` and an exact `If-Match` on subsequent requests. Missing or mismatched `If-Match` produces HTTP 412. An incompatible `If-Range` also produces 412 rather than an unannounced full-body fallback. File sizes above the cap return 413. Source metadata changes detected before and after capture return 409.

**Not a qualified mount or atomic snapshot.** A concurrent in-place writer can change bytes while the initial buffer is captured, including with unchanged file size and modification time. The digest identifies the captured bytes, but does not prove they ever coexisted atomically on disk. This is an experimental, bounded representation consistency improvement, not source-version authority. Each request reopens and rereads the file. There is no persistent snapshot lease, durable revocation state, identity pairing, write isolation, or mount support. A client must reject unexpected HTTP 200 on range operations and validate assembled content. No production data or Tailscale policies should be changed for this experiment.

Before promotion: add atomic source snapshot acquisition or explicitly writer-coordinated copy, file identity and replacement tests, adversarial in-place mutation, quota/concurrency limits, revocation during reads, exact-head Windows/Linux CI and independent hostile security review.
